Finance

Bank reconciliation platform

Statements from two banks arrive by API every night and are matched against the ERP automatically.

Problem

Statements were downloaded by hand, and for one bank every download meant typing a code from a physical security token. Card-terminal accounts produce a very high number of transactions each day, while the ERP records them as a few daily totals, so individual bank lines had nothing to match against. Bookkeeping errors in the ERP, like duplicate entries or documents that were never posted, were found late.

What I built

  • Connectors to both banks: Bank of Georgia over REST with OAuth2, and TBC Bank over SOAP with mutual TLS (client-certificate authentication). The security token is no longer needed.
  • A month-partitioned Parquet store queried with DuckDB, holding 20M+ transactions across dozens of account and currency streams. ERP cash-flow records come in from SQL Server.
  • Matching in passes: tax ID first, then counterparty name similarity, then amount. Anything still unmatched goes to a review list. Card-terminal lines are first rolled up per day and transaction type so they line up with the ERP's daily totals.
  • A nightly job that compares local record counts with the counts each bank reports and re-downloads any gap. It converts foreign currency at each bank's own rates and locks the store while writing, so two runs can't collide.
  • A NiceGUI app, first prototyped in Streamlit, with a Georgian-language interface. It suggests alternate spellings of counterparty names and new matching rules, and exports to Excel or CSV.

Outcome

  • The unexplained difference between bank and ERP is about 0.003% of a month's transaction value.
  • Statements arrive every night without anyone logging in to a bank.
  • Paging through one statement API could return the same records twice. The connector now deduplicates and retries, and the nightly count check confirms nothing is missing or doubled.
  • Duplicate ERP postings and unposted documents appear on the morning exception list instead of turning up weeks later.

Finance · Tax

RS.ge waybill reconciliation

Checks every waybill registered with the Revenue Service against the ERP, and the other way round.

Problem

Georgian companies register their waybills with the Revenue Service (RS.ge), and finance has to confirm that the tax system and the ERP agree in both directions. By hand, that means exporting a date range from each system, matching on waybill number, and remembering which document types shouldn't count.

What I built

  • Login with the user's own RS.ge credentials, checked live against the service, then a date range and a direction: received or issued, normal or returns.
  • The RS.ge side comes from its SOAP API in 3-day chunks fetched in parallel by up to 8 workers, with caching. The ERP side comes from SQL Server stored procedures.
  • A matching engine that first excludes internal transfers, e-invoices and rejected documents, then joins on waybill number and sorts every document into matched, missing in RS.ge, missing in the ERP, or amount mismatch.
  • An email module that sends each counterparty a summary of its discrepancies with a four-sheet Excel attachment, plus Excel export and an admin panel with an activity log.
  • A port from Streamlit to NiceGUI with AG Grid. An automated test runs both matching engines on the same data and confirms the results are identical.

Outcome

  • In use by the finance team. Any date range and direction reconciles in one run instead of a manual comparison across two systems.
  • The interface can change safely, because re-running the equivalence test re-checks the matching logic automatically.
  • Several undocumented RS.ge API behaviors were confirmed with RS technical support and are handled in the fetch logic.

Management reporting · Automation

Hourly sales reports on WhatsApp

Sales tables sent to management and branch staff every hour of the trading day, built on self-hosted n8n.

Problem

Sales data was already in SQL Server, but the people running the stores couldn't see it while the day was still going. Getting numbers to directors, branch managers and channel reps meant pulling a report by hand each time.

What I built

  • Self-hosted n8n, an open-source workflow automation tool, running in Docker. Scheduled triggers run every hour from 11:00 to 23:00 plus a nightly summary, each calling a SQL Server stored procedure.
  • JavaScript Code nodes that turn the rows into color-coded Georgian-language tables for branches, the delivery channel and cafes. A self-hosted Kroki/Graphviz service renders them to PNG. Kroki expects compressed source in the URL, so I wrote a small DEFLATE encoder that runs inside an n8n Code node with no external packages.
  • Images are uploaded through Meta's Graph API and sent with the WhatsApp Business Cloud API, routed by role: management gets the full picture, each branch manager sees only their own branch, and channel reps get their own tables.
  • Cost control built around Meta's 24-hour messaging window: one daily template message with a quick-reply button, a webhook workflow that records the tap, and free in-session image messages after that. Recipients without an open session are skipped.
  • Retries and failure logging on uploads, single-recipient test versions, and Node.js build scripts that generate the workflow JSON instead of editing it by hand.

Outcome

  • Sales tables reach phones 13 times a day plus a nightly summary, with no manual report pulls.
  • Designed so that the only paid message per recipient is the daily opt-in prompt.
  • Changes are generated by script and tried on a test recipient before they go to the full list.

Data platform · Monitoring

SQL Server job monitor

A live dashboard and a 09:00 email showing which overnight SQL Server Agent jobs finished, which failed, and at which step.

Problem

The warehouse depends on scheduled SQL Server Agent jobs that run overnight, each split into several steps. Checking them meant opening job history in SSMS every morning and reading raw error text whenever a step broke.

What I built

  • A read-only data layer that queries only the msdb system tables for jobs, steps, run history and activity. Nothing on the server is changed.
  • A live dashboard served by a small built-in PowerShell web server. Each monitored job shows its latest status, duration and recent runs, refreshing every minute; clicking a past run opens its steps, sorted by duration or by run order.
  • Plain-language failure reasons: common SQL errors such as deadlocks, timeouts, duplicate keys, a full transaction log or type conversion problems are explained in Georgian, with the full error text one click away.
  • A settings panel listing every job on the server. Ticking a job adds it to both the dashboard and the email.
  • A daily 09:00 email report sent by a Windows scheduled task, with a preview mode that writes the email to a file instead of sending it.
  • No dependencies beyond built-in PowerShell: no Python, Node or extra modules, so the folder copies to another machine and runs.

Outcome

  • The morning check is one email instead of a trip through job history in SSMS.
  • A failed step arrives with a likely cause in plain language, so the first question about what broke is answered before anyone opens the server.
  • Adding a job to monitoring is a checkbox, not a code change.

PowerShell · SQL Server Agent · msdb · HttpListener · HTML / CSS / JavaScript · Windows Task Scheduler

Data quality

POS data audit and cashier workload

Checked what the daily load from the tills into the sales warehouse keeps, what it drops, and where history could quietly go missing.

Problem

Sales reporting runs on a warehouse loaded every day from the POS (till) system. Nobody had checked which fields the load carries over or whether years of history were complete. Shift planning also needed an hourly measure of checkout workload, and cashier IDs never reached the warehouse.

What I built

  • A field-by-field map of the core POS source tables against what the daily load (ETL) actually writes. Several operationally useful fields, including cashier IDs, never arrive.
  • A month-by-month completeness check of a sales table with hundreds of millions of rows, compared against the POS system's live and archived data.
  • The cause of the gaps: the daily job reloads only a short recent window and has no way to go back for older days. Without a fix, an outage longer than that window would turn into permanent loss.
  • A reference document covering the data flow, the load-window risk and what a fix requires.
  • Read-only T-SQL against the live POS that turns receipt scan and payment times into receipts, active terminals and active cashiers per branch and hour, giving the minimum number of cashiers each hour needs.

Outcome

  • The load-window risk and the requirements for fixing it were documented and handed over.
  • A verified month-by-month completeness check of the sales history, and a list of POS fields the warehouse doesn't receive.
  • A minimum cashier count per branch and hour, with every timestamp decoding checked against a full real trading day.

E-commerce

Glovo availability checker

Flags products switched off on Glovo that are still selling in the store, using till sales as proof.

Problem

Products were being switched off on Glovo while still in stock and selling in the store, so delivery orders were lost for as long as they stayed off. Glovo's partner platform has no API. The only signal is a daily product-catalog Excel report with around a thousand status changes, too many to check against store sales by hand.

What I built

  • A NiceGUI web app where the e-commerce team uploads the daily report. It pulls out every product marked inactive and the time it was switched off.
  • For each of those products, a read-only query of live till sales between the switch-off time and the report time, through a SQL Server linked server. Barcode lists are split into chunks to stay under query length limits.
  • The stores' own rules built in: receipts after midnight belong to the previous business day, returns and cancellations don't count, and products the ERP sync will switch back on by itself are skipped so they don't raise false alarms.
  • Per-product results (first sale, last sale, number of sales) with Excel export, a history of past checks, and a store-code mapping that saves new codes as they appear.
  • A self-test against real data and a documented always-on internal deployment with its own isolated Python environment.

Outcome

  • On a day checked by hand at one branch, a meaningful share of the products switched off on Glovo were still selling in the store.
  • The check now runs from one file upload, and the e-commerce team doesn't need SQL or database access.
  • Results follow the same business-day and valid-sale rules the stores use, so they match the stores' own numbers.
